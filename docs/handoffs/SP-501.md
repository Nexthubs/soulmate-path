## 1. Scope completed
- **Create/ensure semantics on first successful payment:** SKETCH and REPORT placeholder artifact rows (`generation_status=NOT_STARTED`, `artifact_version=v1`) are created transactionally in the same DB transaction as the first-payment state transition, via `SubscriptionService._ensure_artifacts_initialized` (`backend/app/soulmate/services/subscription_service.py`). Both first-payment paths (webhook `PAYMENT.SALE.COMPLETED` handler and PayPal REST reconciliation) create/ensure the placeholders.
- **Authoritative unlock timestamps (TIME-01):** `sketch_unlock_at = first_payment_completed_at + 12h`, `report_unlock_at = first_payment_completed_at + 24h` (`settings.soulmate_sketch_unlock_hours=12`, `settings.soulmate_report_unlock_hours=24`). Unlock base is `sub.first_payment_at` (authoritative), never the triggering event's renewal time.
- **Duplicate-payment idempotency:** replayed webhook events, the same payment under different event IDs, and webhook-then-reconciliation double processing all leave exactly 1 SKETCH + 1 REPORT row. Uniqueness is enforced at DB level (`uq_soulmate_artifacts_session_type_version`, partial index `uq_soulmate_one_sketch_per_email` from SP-002).
- **Concurrency hardening (SP-501 code change):** `_ensure_artifacts_initialized` previously used an unguarded SELECT-then-INSERT; under simultaneous first-payment delivery (webhook + user-triggered reconcile), the losing insert raised `IntegrityError` at flush/commit and failed the whole webhook/reconcile transaction. It now (a) flushes pending outer-transaction changes first (session runs with `autoflush=False`), (b) wraps each artifact INSERT in a `begin_nested()` savepoint, and (c) on `IntegrityError` re-verifies row existence and tolerates a lost insert race, keeping the outer transaction alive. Unlock timestamps of existing rows are never modified (TIME-01 immutability).
- **Self-healing ensure:** both first-payment paths now call ensure on *every* confirmed payment, not only inside the first-activation branch, so an entitled session with missing artifact rows (partial historical activation / drift) is healed on the next confirmed payment or reconciliation — using the authoritative first payment time.

## 7. High-risk checks when applicable
- **Authorization / ownership:** artifacts are created only via subscription/session-bound paths; no new endpoints; ownership unchanged from SP-403/SP-408 (custom_id strict binding).
- **Idempotency / concurrency:** ensure is idempotent under repeated and concurrent delivery; DB unique constraints are the final guard; savepoint tolerance prevents a lost-insert race from failing the whole webhook/reconcile transaction.
- **Payment / entitlement authority (`PAY-AUTH-01`):** placeholders appear only after a verified `PAYMENT.SALE.COMPLETED` or provider-confirmed reconciliation; `BILLING.SUBSCRIPTION.ACTIVATED` grants nothing (tested).
- **Unlock time authority (`TIME-01`):** unlocks derive from `sub.first_payment_at` (server-persisted, set once); renewals and self-heal never shift existing `unlock_at` (tested).

## 8. Deviations / implementation decisions
- Self-healing ensure (item in scope 1) was an addition over the literal Wave 4 behavior: ensure previously ran only on first activation. It is required by the task's "create/ensure" wording and covers entitled sessions with missing rows; idempotency makes it free in the normal path.
- Reconciliation-activation uses `billing_info.last_payment` as the first-payment time (SP-408 design, reviewed at M2). If a subscription completes 2+ cycles before the FIRST reconciliation AND all webhooks were missed, unlock base would be the latest payment (conservative direction: unlocks later, never earlier). Narrow edge; left unchanged to avoid re-opening reviewed SP-408 logic — flagged below.

## 9. New risks / TBDs / known limitations
- The reconciliation-first-activation edge above: a future hardening (not in this task's scope) could compute the earliest COMPLETED transaction from the transactions API as the authoritative first payment when backfilling.
- If a paid session could ever have an empty `email_normalized`, the sketch placeholder would be keyed to `""`; product flow (email capture + route guards) prevents reaching payment without a bound email. No change made.
