## 1. Scope completed
- **Canonical versioned report content contract** ([`backend/app/soulmate/domain/report.py`](file:///Users/zhaozhao/AI%20Coding/Soumate%20Path/backend/app/soulmate/domain/report.py)):
  - `SoulmateReportV1` Pydantic model implementing DEV-SPEC §13.2 with the acceptance-required schema/version field: `schema_version` (snake_case) ⇄ `schemaVersion` (camelCase via `alias_generator=to_camel`, matching the `SoulmateProfileV1` convention from SP-205). Absent field defaults to `v1`; any explicitly different value is rejected.
  - `SoulmateReportSection` (`index` display label, `title`, `body`, optional `points`) and `SoulmateReportSectionPoint` (optional lead-in `title`, required `body`) — structure verified against Figma node `102:1358` (H1 → `title`, intro paragraph → `intro`, numbered sections `01./02./03.` → `index`, section paragraphs → `body`, "Strong →" lead-in list items → `points[].title`/`body`, decorative `✦ ✦ ✦` end mark → optional `closing` content field, absent in canonical fixture).
  - `parse_soulmate_report_v1(data)` — validates arbitrary payloads (future generator output / stored JSON) and converts pydantic errors into the report error taxonomy.
  - Exports added to `app.soulmate.domain.__init__` (`REPORT_SCHEMA_VERSION`, `ReportValidationError`, section/point models, `parse_soulmate_report_v1`).
- **Plain-text content policy (acceptance: rejects executable HTML/script):**
  - Markup-like content rejected on **every** text field via `</?[A-Za-z][^>]*>` — mirrors real HTML5 tag parsing, so `5 < 6`, `i <3 you`, and `a<b` (no closing `>`) remain valid while `<script>`/`<ScRiPt>`/`<img onerror=...>`/`<iframe>`/`</div>`/`<svg/onload=...>` are refused.
  - Script URL schemes rejected via case-insensitive `\b(javascript|vbscript):`.
  - Policy is **rejection, not sanitization**: failures raise `ReportValidationError` with `details.field` (full in-report path, e.g. `sections.body`, `points.title`) and `details.reason` (`markup_like_content` / `script_url_scheme`) so generation/persistence callers can log precisely. Entity-encoded text (`&lt;script&gt;`) is inert plain text and accepted; the renderer (SP-703) must still render text nodes only.
- **Structural integrity rules:**
  - `extra="forbid"` on all three models — provider payloads or stored JSON with unknown fields are rejected, never silently dropped (protects SP-702 persistence and SP-704 provider boundary).
  - Sections list is the authoritative display order (never re-sorted); `index` is a non-blank display label (≤16 chars) and must be unique within a report.
  - `sections` requires 1–24 entries; empty `points` lists normalize to absent so persisted `content_json` never stores meaningless arrays.
  - Generous length caps as implementation bounds (not product semantics): title/section/point titles ≤200; intro/closing ≤4000; section body ≤8000; point body ≤2000; ≤12 points per section.
- **Frontend type alignment (minimal contract propagation, no renderer work):**
  - `SoulmateReportV1` TS interface (`frontend/src/soulmate/components/report/types.ts`) gained required `schemaVersion: string`; `DEFAULT_REPORT_FIXTURE` sets `schemaVersion: "v1"`.
  - `ReportRenderer.tsx` minimal-variant inline object and the five `SoulmateReportV1` literals in `report-renderer.test.tsx` updated to satisfy the required field. Renderer behavior unchanged (SP-703 owns renderer parity).

## 8. Deviations / implementation decisions
- `schema_version` added beyond the §13.2 TypeScript snippet — required by the task acceptance ("schema/version field"); default `v1` when absent, hard-reject otherwise.
- Length caps, `extra="forbid"`, unique non-blank `index`, and `points: []` → `None` normalization are implementation bounds, not product decisions; all documented in the module docstring and adjustable without semantic change.
- `index` left as a free-form non-blank label (no `NN.` format enforcement) — format is a display-side product choice not fixed by any spec/decision.

## 9. New risks / TBDs / known limitations
- A prose text containing a `<letter…>` sequence closed by `>` (e.g. "if x<y then z>w") is rejected by design; harmless for editorial report content and the safe failure direction. Revisit only if REPORT-02 prompt work shows real false positives.
- Case-insensitive `javascript:` rejection also rejects a literal prose mention of the token; accepted trade-off (editorial soulmate report carries no script-scheme tokens).
