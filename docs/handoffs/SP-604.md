## 1. Scope completed
- **Two-phase worker processing** (refactor of SP-603's single-transaction claim+process, `backend/app/soulmate/services/sketch_generation_service.py`):
  - **Phase A (txn):** claim one QUEUED job (`FOR UPDATE SKIP LOCKED`) → PROCESSING + `locked_at`; load artifact `FOR UPDATE`; completion guard (a COMPLETED artifact short-circuits the job to COMPLETED with **no provider call**); profile load + prompt build (SP-601); invalid/missing profile inputs fail permanently inside this txn (never retried).
  - **Phase B (no txn held):** provider call (SP-602 interface) + `SketchResultSink.persist`.
  - **Phase C (txn, fresh row locks):** guards — job must still be PROCESSING (a result arriving after its claim was reclaimed is discarded, never persisted) and artifact must not have completed via another path; on success §11.3 metadata persisted exactly once.
- **Bounded retry with exponential backoff (§11.6):** retryable failures requeue the job (`QUEUED`, `run_after = now + base * 2^(attempt-1)`, artifact stays PROCESSING → §10.3 GENERATING) until `JOB_RETRY_MAX_ATTEMPTS` (default 3); the final exhausted attempt terminates as `FAILED_RETRYABLE` (final category). Permanent (invalid/safety/policy) failures terminate immediately as `FAILED_PERMANENT` and are never re-claimed.
- **Stale-claim reclamation:** `reclaim_stale_processing_jobs()` requeues PROCESSING jobs whose `locked_at` exceeded `JOB_CLAIM_STALE_SECONDS` (default 600s — worker death mid-call), consuming an attempt under the same budget so crash loops are bounded; budget exhaustion → `FAILED_RETRYABLE` terminal with `error_code=CLAIM_STALE`. Wired into the worker loop before each claim.
- **Idempotency / no-second-owned-sketch guards:** (a) unique idempotency key + advisory lock at enqueue (SP-603); (b) phase-A completion short-circuit; (c) phase-C job-status + artifact-completion guards under row locks; (d) SP-501 DB uniqueness (`uq_soulmate_one_sketch_per_email`, session+type+version). The provider call remains at-least-once (documented residual: provider spend, never a second owned asset).
- **Observability (§19.1):** attempt counts on job + artifact, `error_json` per failure (message/error_code/retryable/provider_code/provider_request_id/attempt), structured warnings with job/artifact ids; provider raw errors stay server-side (§19.3 — `ArtifactStatusView` exposes no error fields).
- **Configuration (§22 group 8, additive):** `JOB_RETRY_MAX_ATTEMPTS=3`, `JOB_RETRY_BASE_BACKOFF_SECONDS=5.0`, `JOB_CLAIM_STALE_SECONDS=600.0` + `.env.example` entries.
- **Test-hermeticity fix (SP-602 tests):** the product owner's real `.env` (OPENAI_BASE_URL/API_KEY for IMGPROVIDER-01) is now present when pytest runs from the repo root and `Settings` loads it — three provider tests that implicitly assumed empty env config were made hermetic (explicit `monkeypatch` of the five §22 image settings / API key; URL-fallback mock routes by path suffix `…/images/generations` instead of a fixed prefix). Assertions unchanged in strength; no production code touched.

## 8. Deviations / implementation decisions
- **Two-phase instead of SP-603's single-transaction claim+process:** required for honest attempt accounting (a committed claim survives a mid-call crash so the reclaim path can count it) and stale-PROCESSING reclamation. Crash-safety is preserved: an uncommitted claim rolls back; a committed claim is reclaimed with backoff.
- **Reclaimed-crash attempts consume the retry budget** (a dead worker's attempt is a real attempt; the provider may have been called).
- **Unknown phase-B exceptions classify as retryable** (bounded by the budget) rather than permanent — a transient DB blip must not kill a paid generation.
- **Hermeticity fix** in SP-602 tests (see §1) — environment-dependent test setup, not a behavior change.

## 9. New risks / TBDs / known limitations
- If `JOB_CLAIM_STALE_SECONDS` is configured below the real provider call duration, a slow in-flight generation could be reclaimed and re-run (double spend; the duplicate is discarded by phase-C guards). Keep stale >> provider timeout (defaults: 600s vs 120s).
- Terminal `FAILED_RETRYABLE` jobs require support/manual requeue (no automatic resurrection); SP-607's failed-state UX must not imply automatic retry.
