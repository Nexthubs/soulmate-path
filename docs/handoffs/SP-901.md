## 7. High-risk checks when applicable

- Authorization / ownership: N/A — no new endpoint or query surface; the one added DB read (`subscriptions.session_id` by PK) happens inside the ledger service's existing locked transaction and is used only for the anonymous session correlation §18.2 prescribes.
- Idempotency / concurrency: `soulmate_payment_confirmed` fires only on the first durably recorded COMPLETED payment (cycle 1); duplicate provider payment IDs return early before the emission. Generation events fire from fenced phases only (stale/discarded claims never emit); terminal-only failure emission avoids retry-loop inflation.
- Failure / retry: analytics is best-effort on both sides — backend `track_funnel_event` swallows exceptions after logging; frontend wrapper try/catches everything; a broken sink cannot break checkout, generation, or cancellation flows.
- Payment / entitlement authority: no change — `soulmate_paypal_approved` remains a client funnel observation only (PAY-AUTH-01 untouched); the server-side confirmation event is emitted from the ledger, the authoritative record.

## 8. Deviations / implementation decisions

- **Event naming follows DEV-SPEC §18.1 (canonical `soulmate_` names)** rather than TASK-BREAKDOWN's shorthand list; the mapping is recorded above. TASK-BREAKDOWN's `payment_started`/`payment_success`/`sketch_generated`/`checkout_click` are covered by `soulmate_paypal_approved`/`soulmate_payment_confirmed`/`soulmate_sketch_generation_completed`/`soulmate_paypal_start`.
- **Default sink drops in production** until a provider/collector is approved (open `ANALYTICS-01`). The wrapper accepts an injected sink so M6 can wire one without touching instrumented pages.
- **Unlock events are client-side and tab-session deduplicated** (`sessionStorage`) rather than server-persisted "seen" flags: funnel analytics is best-effort by contract and this avoids a new durable write path. Multiple tabs/devices may double-count unlock events; payment confirmation and generation lifecycle remain server-authoritative exactly-once.
- **`soulmate_sketch_viewed.artifact_version` is `null`** because the artifact status API does not expose the version; no API change was made to keep SP-901 scope-contained (SP-902/M6 QA may extend the response).
- **Pre-existing `interstitial_answered` / `email_captured` backend logs left untouched** (§19 observability, not §18.1 funnel events; funnel steps for those moments are client-emitted to avoid double counting).

## 9. New risks / TBDs / known limitations

- `ANALYTICS-01` (OPEN, added to `DECISIONS.md`): production analytics transport/sink — until resolved, production funnel data is not captured anywhere.
- Unlock/one-shot dedupe is per tab session; cleared storage or a new tab can re-fire `quiz_started`/`sketch_unlocked`-class events (acceptable funnel noise; server events unaffected).
- `soulmate_question_answered.duration_ms` uses the client clock (duration of a user interaction; TIME-01 governs entitlement timing, not telemetry timing). Unlock `hours_since_payment` uses server timestamps only.
