  - result (`app/soulmate/result/page.tsx`): `soulmate_result_view` once per authorized session during a component mount + unlock tracking on each fresh server aggregate, so a `LOCKED → UNLOCKED` refetch emits the appropriate event; `hours_since_payment` derives from server timestamps only (§18.2/TIME-01);
  - sketch/report pages: `soulmate_sketch_viewed` / `soulmate_report_viewed` once per authorized session during a component mount, plus unlock first-view fallbacks; leaving and reopening a page starts a fresh view; Sketch includes the persisted `artifact_version` from its authorized status response;
  - settings (`SubscriptionSettingsAction.tsx`): `soulmate_subscription_cancelled` (provider_status from the server cancel response).
- **Server-authoritative instrumentation (4 events):**
  - `soulmate_payment_confirmed` — `PaymentLedgerService.record_payment` detects whether any earlier successful payment exists (FAILED rows do not count); it queues the event for the outer transaction commit, so an activation failure/savepoint rollback does not emit a false confirmation;
  - `soulmate_sketch_generation_started` (model, prompt_version) — `_claim_and_prepare` post-commit;
  - `soulmate_sketch_generation_completed` (latency_ms, attempts) — `_finalize_success` post-commit, inside-fence wins only;
  - `soulmate_sketch_generation_failed` (error_code, attempts) — terminal failures only (permanent errors, budget-exhausted crash-loop termination); bounded retryable requeues stay off the funnel.
- **Session-scoped dedupe:** `trackArtifactUnlocked` uses `sessionStorage` keys containing the artifact kind and authorized public session ID. View events use a caller-owned `Set` in each page component's `useRef`, keyed by event and authorized session ID. Authenticated Result, Sketch, and Report responses expose that ID even for cookie-only requests, and navigation carries it through. Pages ignore a prior session's response during a route switch. A missing ID suppresses the corresponding event. Repeated aggregates/status updates and A → B → A switches during one mount do not duplicate a session view; unmounting and reopening creates a fresh set and records the revisit.

## 4. Contract impact

- **API:** existing Result, Sketch, and Report status response schemas include the authenticated session's public `session_id`; completed Sketch status also returns its persisted version. Authorization rules are unchanged. This lets cookie-only clients deduplicate events and preserve identity through Result → artifact navigation. `soulmate_payment_confirmed` still reads `subscriptions.session_id` inside the existing locked ledger transaction.
- **Types / schemas:** frontend gains `SoulmateFunnelEventMap` (including a required string `artifact_version` for Sketch views); backend gains `FUNNEL_EVENT_PROPERTIES` and the optional Sketch response version. Both are documentation-by-code of DEV-SPEC §18.1 and drift-pinned by tests on each side.
- **Configuration:** none (no new env keys; sink selection uses `NODE_ENV`).
- **DB / migration:** none.

## 7. High-risk checks when applicable

- Authorization / ownership: existing session ownership checks are unchanged; public `session_id` is included only in the already-authorized Result/Sketch/Report response for that session. The added DB read (`subscriptions.session_id` by PK) happens inside the ledger service's existing locked transaction and is used only for the anonymous session correlation §18.2 prescribes.
- Idempotency / concurrency: first-success detection ignores FAILED rows and runs while the subscription payment lock is held; duplicate provider payment IDs return early. The queued callback skips SAVEPOINT commits, is discarded if its originating transaction/savepoint rolls back, and emits at outer commit. Regression tests cover activation failure followed by successful webhook retry. Generation events fire from fenced phases only (stale/discarded claims never emit); terminal-only failure emission avoids retry-loop inflation.
- Failure / retry: analytics is best-effort on both sides — backend `track_funnel_event` swallows exceptions after logging; frontend wrapper try/catches everything; a broken sink cannot break checkout, generation, or cancellation flows. The commit callback also catches transport errors after the payment is committed.
- Payment / entitlement authority: no change — `soulmate_paypal_approved` remains a client funnel observation only (PAY-AUTH-01 untouched); the server-side confirmation event is emitted from the ledger, the authoritative record.

## 8. Deviations / implementation decisions

- **Event naming follows DEV-SPEC §18.1 (canonical `soulmate_` names)** rather than TASK-BREAKDOWN's shorthand list; the mapping is recorded above. TASK-BREAKDOWN's `payment_started`/`payment_success`/`sketch_generated`/`checkout_click` are covered by `soulmate_paypal_approved`/`soulmate_payment_confirmed`/`soulmate_sketch_generation_completed`/`soulmate_paypal_start`.
- **Default sink drops in production** until a provider/collector is approved (open `ANALYTICS-01`). The wrapper accepts an injected sink so M6 can wire one without touching instrumented pages.
- **Unlock events are client-side and per-session/per-artifact tab-session deduplicated** (`sessionStorage`) rather than server-persisted "seen" flags. Result-to-artifact navigation preserves the public session ID. A missing session ID suppresses the event until an authorized status response supplies the stable ID.
- **View events are client-side and per-event/per-session deduplicated only for one page component mount** using a caller-owned `Set` in `useRef`, not `sessionStorage`. A missing ID suppresses the event until an authorized status response supplies the stable ID. Unmounting and reopening the page allows the same session's view event again. The current artifact status derivation recognizes `v1`, so current completed Sketch views send the persisted `v1` value.
- **First-payment confirmation is emitted after the root transaction commits.** It remains best-effort; a process crash after commit but before the callback runs can lose telemetry without affecting payment or entitlement persistence.
- **Pre-existing `interstitial_answered` / `email_captured` backend logs left untouched** (§19 observability, not §18.1 funnel events; funnel steps for those moments are client-emitted to avoid double counting).

## 9. New risks / TBDs / known limitations

- `ANALYTICS-01` (OPEN, added to `DECISIONS.md`): production analytics transport/sink — until resolved, production funnel data is not captured anywhere.
- Unlock one-shot dedupe is per tab session and keyed by artifact + public session ID; cleared storage or a new tab can re-fire events (acceptable funnel noise; server events unaffected).
- View-event dedupe is scoped to each page component mount and keyed by event + authorized public session ID; a later mount records another view as required by §18.1.
- `soulmate_question_answered.duration_ms` uses the client clock (duration of a user interaction; TIME-01 governs entitlement timing, not telemetry timing). Unlock `hours_since_payment` uses server timestamps only.
