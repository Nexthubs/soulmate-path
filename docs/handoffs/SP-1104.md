## 1. Scope completed
- **`stepPreparation.ts` (new, pure):** in-memory per-`sessionId+step` preparation store — `ensure` reuses ready AND in-flight promises (§6.2.3), only errored entries retry, a resolved response never overwrites a newer entry for the same key, `invalidateExcept`/`clear` implement the Back/new-step/new-session invalidation rules (§6.2.4). Consumers still validate `session_id` + `current_step` against the step they intend to visit (server authority).
- **`SharedFlowContext.tsx`:** now expresses exactly the plan's three responsibilities — session + pinned config; last server-confirmed step + immutable answers snapshot; the preparation store facade. Adds `confirmAnswer` (immutable snapshot update + confirmed step + prune), `confirmStep`, `bumpOp`/`isCurrentOp` (local op sequence for stale-response discarding only — a stable ref, never an authority), `ensurePrepared`/`getPrepared`. All actions have stable references; no localStorage.
- **`flowTargets.ts` (new):** single step-code → route derivation + `prefetchFlowRoute` used by both pages (§6.5, no second step mapping).
- **Quiz → Transition (§6.3):** on answer confirmation the target transition's flow state is fetched once **in parallel with the 150ms dwell**; the loading page consumes the prepared result instead of refetching; answer snapshots update immutably (local + shared — the old `sessionData.answers[x] = …` mutations are gone); the post-dwell advance is discarded if a newer local operation (Back/another submit) superseded it.
- **Transition → Quiz (§6.3):** Continue confirms the resolved step and prefetches the target; the quiz warm path adopts it **only when the confirmed step equals the URL code** — refresh/history/foreign deep links fall through to the existing cold server recovery (§6.4).
- **Continue enablement (§6.4):** the loading page derives its session synchronously from the provider (warm entries have no effect round-trip) and validates against the prepared entry at FIRST render — warm Continue is enabled on first paint; cold entries keep the existing recovery flow; mismatched prepared states route via the existing `routeToServerStep`.
- **Transition-5:** popup chaining and interstitial flow untouched; a `continued` flag releases the warm pin once step 5 has continued so the popup flow keeps consuming the continue response's fresh flow state (§6.3.4).
- **409 / Back / session changes:** Back bumps the op sequence and confirms the server step (pruning mismatched preparations); continue's 409 path still re-syncs with a direct (uncached) `getFlowState`; a different `setSession` id clears all preparations.

## 8. Deviations / implementation decisions
- `warmValidated` was initially an effect dependency; the first browser pass showed a wasted flow-state refetch when `confirmStep` pruned the CURRENT page's entry on departure (effect re-armed while still mounted). Fixed by removing it from the deps (ready entries resolve instantly anyway) and always materializing the consumed entry into `fetchedFlowState` as the fallback source — verified by the follow-up network log (no refetch after continue).
- The loading page now derives `sessionId` synchronously (`createdSessionId ?? sharedFlow.sessionId`) instead of copying it into local state in an effect — this is what makes first-render Continue enablement possible.
- Quiz cold entry right after T0 still runs one `sessions/current` + the single `quiz/config` fetch (the T0 cold bootstrap stores no session body). Pre-existing behavior, not a warm-path duplicate; left as-is to keep the diff minimal.
- The preparation store intentionally caches the flow-state payload even if `current_step` differs from the requested key — consumers must validate; a mismatched entry routes to the server's actual step.

## 8.1 Audit remediation (Codex review of the uncommitted wave, 2026-09-30)

Four findings against batches 3–4 code; fixes applied to this task's scope (issues 1–3) and to SP-1105 (issue 4, recorded there):

1. **P1 — stale operations survive session switches / unmount (Fixed):**
   - `SharedFlowContext.setSession` now bumps the operation sequence when the session id changes, so every in-flight op from the previous session is superseded (in addition to the existing store clear + confirmed-step reset).
   - `confirmAnswer` accepts the submitting `requestSessionId` and discards confirmations from a superseded session; all three quiz handlers pass it.
   - The quiz advance no longer uses a bare `setTimeout`: the 150ms dwell is an awaited promise guarded by `isCurrentOp(seq) && mountedRef.current`; the loading page's `handleContinue` and `handleModalAnswer` bump their own op sequence and apply the same guard. A component-lifetime `mountedRef` (cleared on unmount) covers the "released after leaving the page" case for quiz and loading alike.
2. **P1 — warm adoption trusted a mismatched URL (Fixed):** the quiz bootstrap's warm path now requires `confirmedStep === urlCode` (strict equality, normal client-side advance). Every other case — refresh, history restore, edited deep link, missing confirmation — falls through to the cold server-recovery path, which re-queries `getCurrentSession` and corrects the URL from the server verdict. (The previous `urlValid` fallback branch was removed.)
3. **P2 — navigation did not wait for the prepared target (Fixed):** all three answer handlers now `await` the transition target's preparation **in parallel with the 150ms dwell** and navigate only after `advanceAfterPreparation` validates `flowState.session_id === sessionId` and `flowState.current_step === expectedStep`. On preparation failure the current content stays with an in-place Retry (`retryAdvance`) that re-prepares and advances WITHOUT resubmitting the saved answer; on a mismatched server step the page routes to the server's ACTUAL step.
   - Verification: production-build funnel walk — T1→q07 warm entry still zero bootstrap calls, q06→T1 preparation fired once and consumed, prep-await advance reached T2/q08, T2 Continue first-render enabled. The mismatch branch itself could not be triggered in a live browser (App Router restores cached component state for `pushState` history entries without remounting); its logic is covered by the strict-equality gate + the long-standing cold path, matching the audit's own isolated-preview methodology — recorded as an E2E limitation, not a pass claim.
