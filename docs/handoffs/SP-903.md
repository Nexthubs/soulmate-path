## 7. High-risk checks when applicable

- **Authorization / ownership:** unchanged. Missing-header and invalid-signature tests reject before receipt creation; the invalid-signature case also confirms the sample subscription was not created or activated.
- **Idempotency / concurrency:** duplicate-event metric is emitted after the existing committed-receipt check; integration test confirms two replay metrics while only one webhook receipt row exists. Existing idempotency/order regression tests remain green.
- **Failure / retry:** the processing-failure test confirms the receipt remains retryable (`processing_error` set, `processed_at` null) while the metric contains only safe categories. The emitter swallows transport errors.
- **Payment / entitlement authority:** no client approval path was added. Latency emits only in `activate_from_payment` when both first-payment and session-success timestamps are absent; unverified events still cannot reach the business dispatch path.

## 8. Deviations / implementation decisions

- Reconciliation mismatch count is an event count per differing dimension, not one count for every reconciliation call. The emitted categories are status, first-payment time, and failed-payment count.
- Failure reason values are mapped from provider codes into a finite category set; unrecognized codes become `other`, and an absent code becomes `unknown`.
- Metrics remain best-effort structured logs, separate from the §18 funnel analytics stream.

## 9. New risks / TBDs / known limitations

- The event stream depends on the existing structured-log pipeline and is not a transactional metrics store. A log sink outage can lose telemetry; alerting/aggregation is left to SP-904.
- A metric may be emitted before the enclosing request transaction's final commit. A later transaction rollback could leave an operational log without a matching durable state change.
- Live PayPal verification, provider delivery/retry, and production log ingestion were not exercised here.
