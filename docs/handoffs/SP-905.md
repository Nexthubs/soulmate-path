## 1. Scope completed
- Added `POST /api/soulmate/support/lookup`, accepting exactly one session ID, normalized email, PayPal subscription ID, or provider payment ID.
- Returned the matching session's payment, subscription, artifact, generation-job, and status-timeline summaries.
- Kept historical timeline entries free of the lookup-time status unless a persisted event timestamp proves the status at that event. Current session/subscription/payment/artifact/job statuses are emitted as `current_status_snapshot` events with `status_context="current_snapshot"`.
- Removed session/artifact/job status timeline entries based only on generic `updated_at`; those fields do not preserve a status transition history.
- Added `timeline_history_complete: false` to the response so support readers know the persisted timestamps provide partial, provable history plus current snapshots, not a complete status-transition audit log.
- Restricted responses to allowlisted status, identifier, amount, and timestamp fields. Email, profile/answer data, provider payloads, generation content, storage keys, provider request IDs, and job error payloads are omitted.
- Hardened existing support ledger endpoints with the same dedicated support-key check and safe response schemas; ledger search now requires a precise identifier and no longer accepts email in a URL.

## 2. Explicitly out of scope / not completed

## 4. Contract impact
- **API:** Added `POST /api/soulmate/support/lookup`; exact one-key request in JSON body; requires `X-Support-Key`. Existing ledger responses now use safe allowlists, and broad status/date-only searches are rejected.
- **Types / schemas:** Added `SupportLookupRequest`, status-only case/timeline response types, and safe ledger HTTP response types. `SupportTimelineEvent.status_context` distinguishes `at_event` from `current_snapshot`; `SupportLookupResult.timeline_history_complete` is false because full transition history is not retained. Email is not part of any response type.
- **Configuration:** Added `SUPPORT_API_KEY`. Production startup rejects missing, short, whitespace-only, or session-secret-reused values; support routes return unavailable if the key is unset/weak/reused in any environment.
- **DB / migration:** No schema changes or migration.

## 5. Acceptance criteria
- [x] Authorized support can find a case by session ID, normalized email, PayPal subscription ID, or provider payment ID.
- [x] Response includes status and timeline summaries without provider payloads/secrets, email, generation content, storage data, or records from unrelated sessions. Timeline entries do not project current state onto past events, and the response flags its history as partial. Ambiguous email matches fail closed with HTTP 409.

## 7. High-risk checks when applicable
- Authorization / ownership: dedicated key required; no development/test bypass; no fallback to `SESSION_SECRET_KEY`; constant-time comparison. Tests cover missing configuration, session-key reuse, missing/wrong support key, and correct key.
- Case isolation: exactly one precise key per request; lookup aggregates only rows linked to the resolved session; ambiguous email with multiple sessions returns 409 without disclosing candidates. Automated tests cover all four lookup keys and a second unrelated session.
- Sensitive data: response schemas omit email, raw payment/webhook payloads, profile/answer data, provider diagnostics, generation input/content, object keys, and job error payloads. Rejected email-bearing bodies are neither echoed nor logged.
- Timeline provenance: creation/recording events do not inherit a mutable current status. Transition status is included only when the stored event timestamp establishes it; otherwise current state is labeled with `status_context="current_snapshot"` at lookup time.
- History coverage: the existing tables do not retain every subscription/artifact/job status transition. The response exposes this as `timeline_history_complete=false`; no past state is inferred from a current status.
- Payment / entitlement authority: read-only lookup only; no payment, webhook, entitlement, asset, or generation state is changed. PAY-AUTH-01 and ASSET-01 behavior remains unchanged.
- Failure / retry: N/A; lookup is read-only.

## 8. Deviations / implementation decisions
- No staff identity or email-masking policy existed beyond the prior `X-Support-Key` header implementation. Reused that header contract with a separate, fail-closed secret; email is normalized against the existing stored field, accepted only in the body, and never returned/logged. Multiple matching sessions require a more precise identifier.

## 9. New risks / TBDs / known limitations
- Provision a dedicated `SUPPORT_API_KEY` (at least 32 non-whitespace characters and distinct from `SESSION_SECRET_KEY`) in every production environment before deployment; production startup now fails without it.
- The existing shared support-key contract does not identify individual staff members in an audit trail; no staff identity provider was present in the task context.
- Full historical status transitions cannot be reconstructed from the current schema. Support clients must treat the timeline as partial evidence and use the labeled current snapshots for current state; durable complete history would require a separate persistence change.

## 10. Dependent-task notes
- Support clients can call `POST /api/soulmate/support/lookup` with exactly one JSON field and the `X-Support-Key` header. Email requests must use this body-based endpoint.
- Do not rely on production support lookup until `SUPPORT_API_KEY` is provisioned in deployment configuration.
