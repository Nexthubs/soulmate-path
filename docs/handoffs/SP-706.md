## 8. Deviations / implementation decisions
- The fenced phase-C content write duplicates `save_completed_report`'s core inside the worker transaction (a cross-transaction `FOR UPDATE` reuse was not possible); semantics are identical (validate → no-clobber → metadata) and that service remains canonical outside the worker.
- Report prompt rendering lives inside the provider (SP-704), so template errors surface as permanent provider failures rather than phase-A failures; phase A still materializes/validates the normalized profile.
- `element`/zodiac handling and all content rules are enforced by the owner's prompt text, not code — code enforces only the ReportV1 contract and the plain-text policy.

## 9. New risks / TBDs / known limitations
- Provider spend is at-least-once on worker death mid-call (same accepted residual as the sketch); the fence guarantees the stored report can never duplicate or mismatch.
- The dev go-live uses the owner's LiteLLM gateway; production keys/endpoints are an M6 configuration item.
- gemma-4-26b may occasionally emit sections outside the 50–90-word guidance — schema/policy validation still gates structure and safety; exact style variance is a product-tuning matter (prompt version bump path is ready).
