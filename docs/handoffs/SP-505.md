## 1. Scope completed
- **Bounded polling while generation pending:** `useResultAggregate` gained a `polling` option (enabled on the live Result page). While any artifact is GENERATING (server combined `status` preferred, orthogonal availability×generation fallback), the hook polls `GET /api/soulmate/result` on an exponential backoff schedule — repo-standard 3s initial (DEV-SPEC §15.8 suggests 2–3s), doubling to a hard 30s cap (`RESULT_POLL_MAX_INTERVAL_MS`).
- **Hard duration bound:** a polling session stops after `RESULT_POLL_MAX_DURATION_MS` (10 minutes); the manual `refresh()` and the SP-504 zero-countdown refetch remain available afterwards. A future generation session (e.g. after Retry) starts a fresh backoff curve.
- **Polling stops on terminal states:** the scheduler decision (`computeResultPollDelayMs`, pure and unit-tested) returns "stop" when no artifact is GENERATING (`hasGeneratingArtifact` false — e.g. COMPLETED/FAILED/READY/LOCKED-only). Payment-pending polling remains owned by the payment-processing page (DEV-SPEC §15.8, SP-410 fixed 2.5s/60s strategy).
- **Polling stops on 403:** authorization/entitlement failures stop polling immediately instead of hammering a forbidden endpoint; transient errors (5xx/network) continue within the backoff/duration bounds.
- **Polling stops on unmount:** the scheduling `useEffect` clears its pending timer on cleanup; in-flight fetches are de-duplicated by the existing `inFlightRef` guard, and every fetch attempt (success or failure) advances the scheduler via `fetchVersion`.
- **No other behavior changed:** countdown calibration (SP-504), zero-refetch signal, 403/error rendering, and the fixture preview mode are untouched.

## 7. High-risk checks when applicable
- **Authorization / ownership:** polling only re-requests the authenticated aggregate; 403 stops polling (no repeated forbidden requests).
- **Idempotency / concurrency:** polling GETs are read-only; in-flight de-duplication prevents overlapping requests; timer cleanup prevents post-unmount fetches.
- **Payment / entitlement authority (`TIME-01`, `PAY-AUTH-01`):** polling never changes unlock semantics — responses only re-derive state from persisted timestamps + server time; zero-countdown behavior unchanged.

## 8. Deviations / implementation decisions
- Polling interval constants live in the hook module (not env config) to mirror SP-410's inline strategy; exported so tests and future tuning can reference them.
- The bounded window resets when polling transitions stop→start (new GENERATING session), so a retry gets a full backoff curve rather than inheriting elapsed time from a previous session.
- Transient errors do not stop polling (they advance the same backoff/duration bounds); only 403 does — 4xx others (e.g. 404 after session expiry) will exhaust the 10-minute window at worst and stop.

## 9. New risks / TBDs / known limitations
- The scheduler effect cannot run under `renderToStaticMarkup`; its decision logic is fully unit-tested and the effect wiring is deliberately thin (single setTimeout + cleanup).
- If a generation takes longer than the 10-minute window, the UI stops auto-updating (manual refresh remains); Wave 6 can extend the window or restart polling from the generate-trigger path if product requires it.
