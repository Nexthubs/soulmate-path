## 1. Scope completed
- **DB-backed durable queue** (no external broker exists — docker-compose runs postgres only; the "existing job system" is the §11.6-shaped `ai_generation_jobs` table from SP-501):
  - `SketchGenerationService.enqueue_sketch_generation(db, session)` (`backend/app/soulmate/services/sketch_generation_service.py`):
    - gates: PAY-AUTH-01 entitlement (`subscription_success_at`), bound email, TIME-01 server-side unlock (`LockedAssetError` 423 before `unlock_at`, on_demand §11.4);
    - idempotency key `sketch:<sha256(email)[:16]>:<artifact_version>` (§11.6) + transaction-scoped advisory lock (`payment_lock(db, "sketch-generate", email)`) — concurrent enqueue attempts converge on one job row (unique key; IntegrityError → re-select);
    - SP-501 self-heal reused for missing artifact rows; COMPLETED artifact short-circuits with no new job (no regeneration on revisit/refresh); artifact transitions NOT_STARTED → QUEUED.
  - `SketchGenerationService.process_next_queued_job(provider, sink, job_id=None)`:
    - claims one QUEUED job with `FOR UPDATE SKIP LOCKED` (FIFO by `created_at`, honors `run_after`) and sets PROCESSING inside the claim transaction;
    - runs the full pipeline in the SAME transaction: profile row → `SoulmateProfileV1` → `build_rendered_sketch_prompt` (SP-601) → `provider.generate_image(...)` (SP-602 interface) → §11.3 persistence → COMPLETED. A crashed worker therefore rolls back to QUEUED automatically (no stuck PROCESSING from process death); the provider call is at-least-once and SP-604 owns duplicate-spend hardening;
    - §11.3 metadata persisted onto `SoulmateArtifact`: `provider`, `model`, `prompt_version`, `input_json` (normalized §11.2 inputs), `provider_request_id`, `generation_started_at`, `completed_at`, `storage_key`, `attempt_count`;
    - failures: `SketchProviderError.retryable` → job `FAILED_RETRYABLE` / `FAILED_PERMANENT` (§11.6); `ProfileValidationError` (missing profile / invalid inputs) → permanent; unexpected exceptions → rollback + permanent; artifact records `generation_status=FAILED`, `last_error_code`, `last_error_message`, `attempt_count`; `error_json` on the job carries message/error_code/retryable/provider_code/provider_request_id for observability.
  - `job_id` optional claim scope (tests + SP-604 targeted reprocessing); production workers omit it.
- **Storage seam (SP-605 slot):** `SketchResultSink` Protocol + `LoggingSketchResultSink` default (logs + drops bytes, storage_key None). ASSET-01 requires SP-605's object-storage sink before production persistence is complete.
- **In-process worker:** `SketchGenerationWorker` asyncio loop + `start_sketch_workers()` / `stop_sketch_workers()` wired into FastAPI lifespan (`JOB_WORKER_ENABLED=true`, `JOB_WORKER_CONCURRENCY=4`, `JOB_WORKER_POLL_SECONDS=2.0`; initial poll delayed by one interval so short-lived lifespans stay harmless).
- **Trigger endpoint (§15.10):** `POST /api/soulmate/artifacts/sketch/generate` (`backend/app/api/soulmate/artifacts.py`) — auth/ownership identical to the Result aggregate (session_id query + ownership check, or cookie token); returns `SketchGenerationResponse {server_time, sketch status view, job_status}`; the request only enqueues — processing happens after the request ends. Mounted under `/artifacts` in the API router.
- **Configuration:** added `JOB_WORKER_ENABLED`, `JOB_WORKER_POLL_SECONDS` (additive to §22 group 8) and `.env.example` entries.

## 7. High-risk checks when applicable
- **Authorization / ownership:** endpoint reuses the SP-503 auth/IDOR pattern (403 tested for anonymous and cross-session access); service re-checks PAY-AUTH-01 server-side regardless of API layer.
- **Client-clock:** unlock check uses the server clock against the persisted `unlock_at` only (TIME-01); tested.
- **Idempotency / concurrency:** unique idempotency key at DB level + advisory lock; concurrent-enqueue convergence tested; claim uses SKIP LOCKED; single-transaction claim/process makes worker crashes self-healing (job returns to QUEUED).
- **No duplicate owned assets:** enqueue refuses COMPLETED artifacts; SP-501 DB uniqueness (one sketch per email) remains the backstop; provider-call at-least-once semantics + duplicate-spend guard are explicitly deferred to SP-604.

## 8. Deviations / implementation decisions
- **Claim+process in one transaction** rather than claim-commit-then-process: smallest crash-safe design without a stale-claim reclaimer (SP-604); consequence — provider call is at-least-once (documented risk for SP-604).
- **Sink seam instead of inline storage:** ASSET-01 storage belongs to SP-605; worker marks artifact COMPLETED with `storage_key=None` under the dev sink (interim, warned). SP-605 replaces the default sink without worker changes.
- **In-process asyncio workers** (lifespan) instead of a separate worker process/redis: matches repo deployment (compose has postgres only); `JOB_WORKER_ENABLED=false` supports a dedicated worker process later.
- **Test claim scoping (`job_id`):** the dev database is shared across test runs; without scoping, the global FIFO claim could pick up leftover QUEUED jobs from earlier runs. An autouse purge fixture removes all `sp603_` seeded rows after each test.

## 9. New risks / TBDs / known limitations
- **Provider-call at-least-once:** a provider success followed by a post-call transaction failure regenerates on retry (provider cost duplication). SP-604 must add the durable "generation succeeded" guard before requeue logic lands.
- Artifacts completed under `LoggingSketchResultSink` have no `storage_key` (dev-only until SP-605); SP-607 must not ship against this state.
- Lifespan workers run inside the API process; heavy generation competes with request handling for the event loop. Acceptable for V1 scale; revisit at M6 if needed.
