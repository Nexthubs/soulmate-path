## 1. Scope completed

Added one attacker-perspective security/IDOR test module covering all six TASK-BREAKDOWN cases against the real FastAPI app (httpx ASGITransport) with two independent live sessions — a paid **victim** and an unpaid **attacker**, each with its own signed `soulmate_sid` cookie:

1. **Access another session by ID** — a 16-endpoint cross-session matrix (`GET/PUT/POST /sessions/{victim}/…` for current/answers/interstitials/flow-state/transitions/back/profile/email/email-summary, plus `?session_id={victim}` variants of result, subscription status, sketch/report reads and generates, and route guard). Every request with the attacker's valid credentials answers `403 FORBIDDEN_OWNERSHIP`. A dedicated write test proves cross-session PUT email/answers mutate nothing (victim email unchanged, no answer row created). Confirm with the victim's `session_id` + a victim-bound PayPal subscription (mocked provider `custom_id=victim`) is rejected and the victim's entitlement row is untouched.
2. **Access another sketch/report** — token-only artifact reads resolve the caller's own session: attacker sees empty own state (no image URL/storage key/content), victim's own read serves their COMPLETED data (control proving the denial is the guard, not breakage). Also proves §20 has no artifact-ID read surface: `/artifacts/{uuid}`, `/artifacts/{uuid}/image`, `/artifacts/sketch/{uuid}` all 404.
3. **Spoof paid/unlocked fields from browser** — (a) §20 client-immutable fields (`subscription_success_at`, `unlock_at`, `provider_status`, `generation_status`, `storage_key`) injected into email/answer bodies are rejected `422` (`extra="forbid"`) and no DB value changes; (b) tampered session tokens (flipped signature, foreign-key HMAC, expired timestamp) all fail `403` — a token cannot be minted without `SESSION_SECRET_KEY`; (c) PAY-AUTH-01 confirm chain: a fabricated PayPal subscription 404s; a provider-APPROVED subscription bound to the caller confirms `200` but `is_paid=false`, `status=PROCESSING`, entitlement stays `NULL`, and `/result` still 403s.
4. **Call generate before unlock (TIME-01)** — a session paid 1h ago gets `423 LOCKED_ASSET` from both `POST /artifacts/sketch/generate` and `POST /artifacts/report/generate`; zero `ai_generation_jobs` rows are created; a stray client-supplied `?unlock_at=1970-01-01T00:00:00Z` query parameter is ignored. An unpaid session gets `403` on both pipelines with no job rows and no artifact rows.
5. **Invalid webhook/signature** — HTTP-level `POST /api/webhooks/paypal` with a structurally valid forged `PAYMENT.SALE.COMPLETED` for an attacker-chosen unbound subscription: (a) missing transmission headers → `400`, (b) present-but-invalid signature (dependency-overridden rejecting verifier) → `400`. Both leave zero business effect: no processed event receipt, no ledger row, no subscription row, entitlement `NULL`.
6. **Manipulate route only without entitlement** — `GET /guard/check` for `/soulmate/result|sketch|report` with an unpaid session returns `allowed=false` with a redirect; the paid victim control returns `allowed=true`. Data APIs deny independently of the guard (cases 1–4), so a bypassed frontend guard cannot expose data.

**Acceptance evidence (no leakage):** every denial is additionally scanned — no victim email, no victim storage key, no report content marker in any denial body. A dedicated existence-oracle test shows a fabricated session ID gets the identical `403 FORBIDDEN_OWNERSHIP` as a real victim session on five key read endpoints (the ownership guard precedes the existence lookup), so attackers cannot probe which session IDs exist.

## 8. Deviations / implementation decisions

- **Email endpoint is `POST`, not the `PUT` shown in the DEV-SPEC §15.5 router table.** The implementation (`app/api/soulmate/sessions.py` `@router.post("/{public_id}/email")`) uses POST; tests use the implemented verb. Recorded here as an observation; no code change made (behavior contract unchanged, frontend already uses POST).
- Denial scans assert against *content markers* (victim email, storage key, report title) rather than exact body equality, so the checks stay valid if generic copy changes.
- The forged-webhook zero-effect assertions are scoped to the forged identifiers (`WH-FORGED-%`, `SALE-FORGED-%`, `I-FORGED-%`) instead of global table counts, so the module is order-independent when run in the full suite.
