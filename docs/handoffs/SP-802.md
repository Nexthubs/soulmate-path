## 1. Scope completed
- **Server-authoritative destination resolution for the drawer's `Soulmate Sketch` entry** (SP-802 routing table):
  - no successful first payment → `/soulmate` — derived from the SP-503 aggregate's **403** (the server's own PAY-AUTH-01 verdict for anonymous/IDOR/unentitled callers);
  - paid, sketch `LOCKED` → `/soulmate/result`;
  - unlocked combined states (`READY` / `GENERATING` / `FAILED`, §10.3) → `/soulmate/sketch` (see deviation note on the "per final UX contract" branch);
  - `COMPLETED` → `/soulmate/sketch`.
- Pure resolvers in `drawer/nav.ts`: `resolveSketchDestinationFromStatus` (§10.3 combined status → route) and `resolveDrawerSketchDestination(aggregate, errorStatus)` (full routing table incl. 403/failure fallback).
- `SoulmateDrawerProvider` now performs **one aggregate fetch per drawer open** (lazy; no fetch on page load, none while closed) and feeds the resolved destination to the shared `AccountDrawer`. Identity is the HttpOnly `soulmate_sid` cookie only — no `session_id` argument, so **no local flag or storage value can influence the outcome** (acceptance criterion).
- Explicit `sketchDestination` prop kept as an override that bypasses resolution (tests/fixture use); default production behavior is server resolution.
- Re-resolves on every open, so a payment/status change while the drawer is closed is picked up on the next open.

## 2. Explicitly out of scope / not completed
- Page-level route guarding (`useRouteGuard` / `guard/check`) — unchanged; it remains the authority when navigating TO high-value pages. The drawer destination selects a target; the target page's guard still makes the final access decision (defense in depth).
- GENERATING-state live polling from the drawer — not needed; the sketch page (SP-607) owns polling after navigation.
- Logout / policy links (still placeholders from SP-801).

## 7. High-risk checks when applicable
- Authorization / ownership: the drawer never renders other users' data and only reads the caller's own aggregate (SP-503 IDOR guards apply server-side). Destination resolution adds no new data exposure.
- Idempotency / concurrency: one fetch per open; a stale in-flight response is cancelled via a `cancelled` flag on close/reopen.
- Failure / retry: aggregate failure (any status incl. 403/5xx/network) falls back to `/soulmate` — the safe non-entitled destination; no client-side entitlement is ever inferred on failure (fail-safe, aligned with PAY-AUTH-01).
- Payment / entitlement authority: unchanged — server 403/200 IS the authority; the drawer adds no entitlement logic of its own (TIME-01 untouched: no client clock involved).

## 8. Deviations / implementation decisions
- **"unlocked/generating → /soulmate/result or /soulmate/sketch per final UX contract"** was resolved to **`/soulmate/sketch`** for ALL unlocked combined states (READY/GENERATING/FAILED/COMPLETED): the sketch page natively renders ready/loading/failed/completed per §10.3 and SP-607, and satisfies the §3 guard in each. `LOCKED` (and unknown status) → `/soulmate/result`, the paying user's home base. Flag for owner confirmation; changing it is a one-line edit in `resolveSketchDestinationFromStatus`.
- The page-level guard endpoint (`/guard/check`) was deliberately NOT used for destination resolution: its no-payment redirect target is `/soulmate/subscribe`, which contradicts SP-802 routing row 1 (`/soulmate`), and it has no generation-state visibility (unlock times only). Guard remains authoritative for page access.
- 403 handling reuses PAY-AUTH-01 semantics rather than adding a "membership flag": the aggregate response is the single source of truth for "no successful first payment".

## 9. New risks / TBDs / known limitations
- While the on-open fetch is in flight the entry shows the previous/default destination (`/soulmate`); an immediate click before resolution lands on the safe default. No spinner/loading state was added (minimal scope).
- `GENERATING` and `FAILED` mappings are unit-tested but were not individually E2E'd (both route to `/soulmate/sketch` like READY/COMPLETED, which were E2E'd on the real backend).
