## 1. Scope completed
- **Canonical report contract moves to the domain layer** ([`frontend/src/soulmate/domain/report.ts`](file:///Users/zhaozhao/AI%20Coding/Soumate%20Path/frontend/src/soulmate/domain/report.ts)):
  - `SoulmateReportV1` / `SoulmateReportSection` / `SoulmateReportSectionPoint` are now owned by the domain module — the TypeScript mirror of `backend/app/soulmate/domain/report.py` (SP-701) and of what `GET /api/soulmate/artifacts/report` serves (SP-702). `components/report/types.ts` re-exports them so all SP-108 consumers keep working; `domain/index.ts` barrel-exports the module.
  - `REPORT_SCHEMA_VERSION = "v1"`, `ReportValidationError` (with `field` context), `parseSoulmateReportV1(data: unknown)`, and the non-throwing `isSoulmateReportV1` type guard.
  - `parseSoulmateReportV1` mirrors the backend contract deliberately:
    - structure: non-blank `title`/`intro`, 1–24 sections with non-blank unique `index`/`title`/`body`, optional points (≤12, required `body`, optional `title`), optional `closing`; `schemaVersion` defaults to `"v1"` when absent and rejects any explicit non-`v1` value; empty `points: []` normalizes to absent;
    - plain-text content policy: markup-like content (`</?[A-Za-z][^>]*>` — mirrors HTML5 tag parsing, so `5 < 6`, `i <3 you` stay valid) and script URL schemes (`javascript:`/`vbscript:`, word-boundary, case-insensitive) are **rejected on every text field**;
    - unknown extra fields are ignored (forward-compatible; the renderer reads only the validated known fields of the returned object), and the backend-owned length caps are intentionally not re-enforced client-side (documented asymmetry — structure/version/executable-content rules are the renderer-safety-relevant ones).
- **Renderer validated-input gate** ([`frontend/src/soulmate/components/report/ReportRenderer.tsx`](file:///Users/zhaozhao/AI%20Coding/Soumate%20Path/frontend/src/soulmate/components/report/ReportRenderer.tsx)):
  - the active payload (initial prop, prop updates, fixture-toolbar variants) passes through `parseSoulmateReportV1` in a `useMemo` before any rendering; the article renders **only** from the validated object;
  - on validation failure the renderer shows a fail-safe state (`data-testid="report-invalid-fallback"`: "Report Unavailable" + ✦ mark + support hint) — no unvalidated field ever reaches a text node; header/back navigation and the celestial end mark remain functional so the user is never stuck;
  - injection safety is layered: the gate rejects executable content upstream, and all content renders as React text nodes (no `dangerouslySetInnerHTML`, no Markdown/HTML interpretation) — entity-encoded text renders escaped and inert.
- **Visual parity preserved:** the Figma 102:1358 editorial markup and styles are untouched by this task (validation wraps the existing JSX; class-level Fidelity tests — amber indices `#b45309`, amber bullets `#f59e0b`, 390px container, `✦ ✦ ✦` end mark — all still pass), so the SP-108-verified parity carries over unchanged.

## 8. Deviations / implementation decisions
- Frontend guard ignores unknown extra fields instead of rejecting them (backend is `extra="forbid"`): the renderer reads only known fields of the object it returns, so unknown fields can never reach the DOM, and a forward-compatible backend addition cannot break rendering.
- Length caps are not re-enforced client-side (backend owns them); the renderer-safety-relevant rules (structure, version, executable-content rejection, unique indexes) are enforced.
- `parseSoulmateReportV1` normalizes `points: []` to absent, mirroring the backend, so persisted data and client validation agree.

## 9. New risks / TBDs / known limitations
- Same false-positive trade-offs as the backend policy (prose like "if x<y then z>w" or a literal "JavaScript:" token is rejected → fallback state); acceptable for editorial content and the safe failure direction.
