## 1. Scope completed
- **`ObjectStorageSink`** (`backend/app/soulmate/services/object_storage_sink.py`) — S3-compatible implementation of the app-owned `SketchResultSink` seam (SP-603), covering AWS S3 and endpoint-compatible services (MinIO etc.) via `OBJECT_STORAGE_ENDPOINT`:
  - uploads `result.image_bytes` (never `result.source_url`) with `put_object(Bucket, Key, Body, ContentType)` through `asyncio.to_thread` (boto3 is sync; the worker event loop is never blocked);
  - **§11.7 key layout:** `soulmate/sketches/{artifact_id}/original.<fmt>` — deterministic per artifact, so revisits resolve to the same stored object (ASSET-01);
  - boto3 client with standard-mode retries (3 attempts) built lazily from §22 group 7 configuration; constructor injection kept for tests.
- **Payload validation rules** (the repo's first storage rules, established here per acceptance "existing storage rules"):
  - declared format must be `webp`/`png`/`jpeg` (§22 `SOULMATE_IMAGE_FORMAT` engineering defaults), mapped to `image/webp|png|jpeg` content types;
  - magic-byte sniffing must match the declared format (RIFF/WEBP, `\x89PNG`, `\xff\xd8\xff`) — relabeled or corrupted payloads never become the durable asset;
  - size must be within `[MIN_SKETCH_BYTES=512, MAX_SKETCH_BYTES=10 MiB]`.
  - violations raise `SketchStorageError` (sanitized message/details for durable error records; `internal_message` for server logs only, §19.3 spirit); the worker classifies them as retryable under the SP-604 budget, satisfying §19.2's "storage upload failure" alertability.
- **Stable URL derivation:** `build_public_object_url(key)` builds `OBJECT_STORAGE_PUBLIC_URL_PREFIX + "/" + key` at read time — URLs are never baked into stored data (DOMAIN-01 spirit). `artifact.storage_key` remains the persisted canonical metadata.
- **Worker binding:** `build_default_sketch_sink()` returns `ObjectStorageSink` when `OBJECT_STORAGE_BUCKET` + keys are configured (production/ASSET-01 path) and `LoggingSketchResultSink` otherwise (dev fallback with warning; bytes dropped, `storage_key=None`). `SketchGenerationWorker` now defaults to this binding — no worker-code change needed when storage config appears.
- **Dependency:** added `boto3==1.43.103` to `backend/requirements.txt` (repo pins exact versions); transitive botocore/s3transfer installed. No SigV4 hand-rolling — battle-tested SDK for payment-adjacent asset durability.
- **Interface:** `SketchResultSink` is now `@runtime_checkable` (consistent with `SketchImageProvider`), enabling conformance assertions.

## 7. High-risk checks when applicable
- **Asset durability (ASSET-01):** bytes uploaded immediately after generation within the phase-C-guarded pipeline; deterministic keys; object never rewritten (a second successful upload to the same key would require a second completed generation, which SP-604's guards preclude).
- **Secrets hygiene:** access/secret keys exist only in the sink instance for the boto3 client; errors carry bucket+key only; SDK internals stay in `internal_message` (server logs).
- **Failure/retry:** upload failures → `SketchStorageError` → retryable under the §11.6 budget (bounded, alertable per §19.2); validation failures of provider output are likewise bounded-retryable (regeneration may produce valid bytes).
- **Authorization/payment:** unchanged (upload is server-side, keyed by server-generated artifact id; no client input reaches the storage path).

## 8. Deviations / implementation decisions
- **boto3 instead of httpx+SigV4:** the repo's PayPal client pattern uses raw httpx, but hand-rolled SigV4 carries real correctness risk for the ASSET-01 durability guarantee; boto3 (via `asyncio.to_thread`) is the standard, tested choice. One exact-pinned dependency added.
- **Validation rules established here** (format whitelist, magic-byte match, 512 B–10 MiB) — no prior storage rules existed; values chosen as engineering defaults per §11.7's "工程默认值" clause and are config-independent constants.
- **Sink failure classification:** validation/upload failures surface as retryable (bounded) rather than permanent — storage hiccups and one-off provider corruption recover on retry; genuinely persistent failures terminate as FAILED_RETRYABLE after 3 attempts (observable, not looping).

## 9. New risks / TBDs / known limitations
- If the sink fails after a successful provider call, the SP-604 retry re-runs the provider (spend duplication) — shared at-least-once semantics; reducing this requires persisting provider evidence before upload (future hardening, not required by acceptance).
- `MAX_SKETCH_BYTES=10 MiB` and the format whitelist are code constants; changing them later is a one-line change but not configurable per environment (no decision requires it).
- Live storage credentials absent in dev: the M4 milestone gate must include one real upload + read-back against the deployment's storage endpoint.
