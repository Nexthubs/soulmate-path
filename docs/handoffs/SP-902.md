## 1. Scope completed

- **Central metrics emitter** — new `backend/app/soulmate/metrics.py`: every generation metric is emitted through the §19.1 structured log pipeline as one stable `event_type="generation_metric"` record with the metric name and allowlisted fields in `extra_data`. Per-metric field allowlists are declared once (`GENERATION_METRIC_FIELDS`); unknown metrics/fields are dropped; emission is best-effort (never raises into business code). This is the raw stream SP-904 alerts will key on.
- **Emission points** in `sketch_generation_service.py` and `report_generation_service.py` (sketch and report pipelines):
  | Metric | Point | Fields |
  |---|---|---|
  | `enqueue_created` | new job committed (`enqueue_sketch_generation`) | job_type |
  | `enqueue_duplicate` | re-enqueue converging on the existing job (idempotency conflict) | job_type |
  | `queue_latency_ms` | successful claim (phase A post-commit) | job_type, latency_ms (enqueue→claim), attempt |
  | `generation_success` | fenced completion (phase C post-commit) | job_type, latency_ms (winning claim→durable completion), attempts |
  | `generation_retry` | retryable failure requeued with backoff | job_type, error_code, attempt, backoff_seconds |
  | `generation_final_failure` | terminal failure (budget exhausted / permanent / crash-loop claim termination) | job_type, error_code, attempts |
  | `generation_user_retry` | explicit user requeue of a FAILED_RETRYABLE job | job_type, attempt |
  | `generation_stale_reclaimed` | stale-claim reclamation count | job_type, count |
  The same eight metrics are emitted for `SOULMATE_SKETCH` and `SOULMATE_REPORT`. Both workers use the same job-type discriminator and schema; metrics are additive and best-effort.
- **DB aggregation service** — new `GenerationMetricsService.summary(db, job_type, since, until)` (`backend/app/soulmate/services/generation_metrics_service.py`): read-only computation of the SP-902 metric families from durable state —
  - counts by job status (queued/processing/completed/failed_retryable/failed_permanent), total enqueued in the window (window = job `created_at`);
  - retry accounting: `jobs_retried` (attempt > 1) and `retries_total` (Σ attempts−1);
  - **final failure rate**: (FAILED_RETRYABLE + FAILED_PERMANENT) / finalized jobs; `None` when nothing finalized;
  - **queue latency** (avg/p50/p95/max/samples): artifact `generation_started_at` (persisted first-claim time) − job `created_at`;
  - **generation latency** (avg/p50/p95/max/samples): artifact `completed_at` − `generation_started_at` for COMPLETED artifacts (first claim → durable completion across all attempts; per-attempt provider latency stays on the log stream).
- Exported `GenerationMetricsService` / `GenerationMetricsSummary` / `LatencyStats` from `app.soulmate.services`.

## 8. Deviations / implementation decisions

- **Python-side percentile computation** instead of `percentile_cont` SQL: keeps the aggregation portable and trivially testable; windows are operational-sized. Documented in the module docstring.
- **Two latency definitions** (stream vs summary) are intentional: the stream measures the winning attempt (per-attempt signal); the summary measures first-claim→completion (the user-perceived end-to-end time across retries). Both are labeled in the schema.
- **Queue latency derives from `artifact.generation_started_at`** (the persisted first-claim time) rather than adding a new "first_claimed_at" column — no migration, exact semantics (first claim, not last).
- **User retries are counted as retries** (`generation_user_retry` + `attempt` accounting), consistent with §10.3 where a user retry grants one more claim.

## 9. New risks / TBDs / known limitations

- `summary()` on a very large window scans all jobs of the requested type in it (two indexed light queries + latency row fetches); operational windows should be bounded until M6 decides retention. Percentile math is O(n log n) in memory on fetched values only.
- Metrics stream has no external consumer yet (SP-904 pending) — values are observable only via structured logs today.
- Shared dev DB caveat for future test authors: `summary()` aggregates per job_type across the whole database — always scope test assertions with `since` (mirrors the SP-603 `job_id` claim-scoping rationale).
