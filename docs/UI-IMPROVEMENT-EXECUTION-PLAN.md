## 1. 目标、范围与默认选择

本轮目标：让问卷在不同屏幕上保持连续背景；点击选项时保持清晰反馈；减少 quiz 与 transition 切换中的中间加载画面；保证日期滚轮显示值和提交值一致。

核心范围：`/soulmate/quiz`、`/soulmate/loading`、Transition-5 弹窗，以及它们进入 email 的直接边界。修改共享 layout 时，要回归其他 soulmate 页面，但不扩展到支付、结果、Sketch、Report 的视觉重设计。

默认采用以下选择，避免实施时猜测产品行为：

- 保留 390px 下既有内容宽度、24px 问卷左右留白、字号、文案及选中样式；背景先扩展到全屏。
- 较宽设备的正文仍居中限宽。首轮保留既有内容宽度，不直接改为 420px 或复制 Stella 的字号。内容扩宽作为后续独立视觉调整。
- 保留现有单选成功后 150ms 反馈，遵循 DEV-SPEC §4.2。首轮不采用 280ms 并行等待。
- 保留现有 q→q 的客户端切题和 URL 历史行为；不顺带改浏览器返回键语义。
- 不增加动画依赖，不为掩盖加载而增加强制过场动画。
- 不修改后端接口、数据库、付费和权限规则。服务端确认后才能推进步骤。
- 不因“已知目标步骤”而假设动态 metadata 已存在，不用 fixture 数据补线上内容。

以下批次编号仅供本方案排序，不是已经登记或授权实施的 SP Task。实际实施时在 `TASK-BREAKDOWN.md` 登记范围、依赖、验收与上下文引用；交付按 AGENTS.md 创建对应 handoff。此方案不修改既有任务或里程碑状态。

## 2. 修正对标结论

| 原分析 | 修订后的实施依据 |
|---|---|
| 每一帧像素位移都触发整页更新 | 当前只在计算行索引与已选索引不同时回调；仍值得隔离父级更新，但严重掉帧需性能记录证明 |
| Next 路由硬跳转导致闪屏 | 当前是客户端路由导航；已有统一暖色 fallback 和共享 bootstrap 缓存。剩余问题是内容替换、目标数据准备及按钮等待 |
| Stella 的 320ms 可直接移植 | 公开脚本中的客户端保存与路由推进，不能替代本项目的服务端确认；本项目先保持现有时序 |
| RAF / GPU 样式能保证 60fps | RAF 不等于滚动结束防抖；硬件加速样式不能替代测量或保证帧率 |
| 仅改四个文件就解决全屏背景 | 必须同步路由 fallback，并检查共享 layout 影响的页面、drawer、弹窗和 guard/error 状态 |
| Continue 可以统一立即启用 | 仅允许有当前会话、当前步骤确认依据且必要数据齐备的正常推进路径；直接访问和刷新仍需服务端恢复 |

## 4. 批次 1：背景与安全区

**优先级：高**

### 修改范围

- `frontend/src/app/layout.tsx`：检查并配置 `viewportFit: "cover"`。
- `frontend/src/app/globals.css`：添加复用的视口和安全区样式。
- `frontend/src/app/soulmate/layout.tsx`：取消公共外壳对全屏背景的 390px 限制。
- `QuizShell.tsx` / `TransitionShell.tsx`：分离全宽背景层与居中内容槽。
- `FlowShellFallback.tsx` 与 quiz/loading/email 的 `loading.tsx`、inline Suspense fallback：背景一致性。
- 受共享 layout 影响的其他页面：仅做必要的背景/限宽兼容修正。

### 具体实现

1. 公共 layout 提供全宽宿主，不给所有子路由强制套同一个渐变。Quiz、Transition 共享当前暖色背景；email 等页面继续使用自己的背景。
2. 同一页面的背景、内容外壳和 fallback 使用同一套颜色与视口规则，避免只修正文、导航中间仍出现窄背景。
3. 内容槽与外层背景分离：390px 保持当前几何布局；320px 可收缩；430px、平板和桌面背景覆盖视口、内容居中，不随屏幕无限拉宽。
4. 背景最低高度提供 `100vh` 回退，支持时使用 `100dvh`。需要稳定高度的内容排布可使用 `100svh`，逐个壳层验证，不全站机械替换。
5. 底部留白使用“现有基础留白 + safe-area-inset-bottom”；顶部在确有贴边内容时同样处理。避免层层重复累加安全区。
6. 首轮保留 footer 正常文档流，不直接复制 Stella 的 fixed Dock。长选项页必须可滚动，最后一个选项不能被按钮遮挡。
7. 检查 drawer、弹窗遮罩和背景的定位基准；检查 email 输入键盘弹出时按钮、滚动和可视内容。

### 验收

- 320 / 375 / 390 / 430 / 768 / 1440px 无横向溢出，背景覆盖完整视口，无意外窄白卡片或边缘阴影。
- 390px 基准下，标题、选项和按钮几何布局未因背景改造发生未经确认的变化。
- Quiz / Transition 正文与加载态底色连续。
- 真实 iOS 的安全区、地址栏展开/收起与旋转可用；Android 地址栏和键盘场景可用。
- 共享 layout 下的其他页面保留自身背景，guard/error 页面无明显背景回退。

## 5. 批次 2：提交反馈保持稳定

**优先级：高**

### 修改范围

`OptionCard.tsx`、`quiz/page.tsx`，必要时调整 `TransitionShell.tsx` 的按钮提交态。

### 具体实现

1. 将“提交期间锁定操作”与“选项真正不可用”分开表达。提交期间整组选项保持原来的视觉状态；真正禁用的选项保留其禁用样式。
2. 即时显示选中边框和勾选状态，保留键盘焦点与可访问名称；逻辑锁同时阻止指针、键盘和重复 handler 调用，不能只依赖 `pointer-events`。
3. 保留服务端成功后 150ms 再切题，不增加额外动画等待。慢请求期间保持当前页面内容，禁止全页 skeleton 或整体降低透明度。
4. 提交超过约 400ms 时显示局部提交提示；该时间只控制提示出现，不控制步骤推进。结束、失败、离页时清理计时器。
5. 请求失败：当前选择保留、解除锁、显示原地错误与重试。重试仍经过现有服务端接口。
6. Continue 也保留正文，仅按钮显示提交状态并防重。`active:scale` 仅在确认视觉需求后添加，不作为消除闪烁的必要措施。

### 验收

- 点击后整组选项不变灰，选中状态在等待期间稳定可见。
- 快速点击/键盘激活不会产生并行重复提交或多步跳转。
- 延迟请求不替换正文；失败不跳页，重试成功后继续正常推进。
- 单选成功后的停留仍为现有 150ms；日期和多选保留自身提交行为。

**可选时序调整：** 若后续希望改成“从点击时起保证最低驻留时间”，需在 DECISIONS 中明确它对 §4.2 的覆盖，再改代码和相应测试。本方案默认不执行这项。

## 6. 批次 3：阶段切换的数据准备与缓存

**优先级：高；依赖批次 2**

### 修改范围

`SharedFlowContext.tsx`、`quiz/page.tsx`、`loading/page.tsx`，以及最小的共享步骤准备辅助模块。保持 API 签名不变。

### 6.1 明确缓存的职责

共享状态分别表达：

- 当前会话与固定 quiz 配置；
- 最近一次服务器确认的步骤、答案快照及本地操作序号；
- 为特定 `sessionId + step` 准备的 metadata，以及 idle/pending/ready/error 状态。

本地操作序号只用于丢弃过期异步响应，不充当服务端版本或授权。缓存仅保存在当前页面生命周期的内存中，不新增 localStorage 持久化。

### 6.2 同步服务器确认结果

1. 每次 answer、continue、navigateBack 成功，基于对应 API 的已确认结果更新快照。答案以不可变方式更新；不要继续直接修改 `sessionData.answers`。
2. `AnswerSubmitResponse.next_step` 可以确认推进目标，但不代表 metadata 已取得。Continue 响应中的 `flow_state` 可作为对应步骤的确认依据。
3. 同会话、同目标的准备请求复用 in-flight promise，避免出发页和目标页各发一次相同请求。
4. 新会话、退出、409 恢复、Back 或新步骤确认会使不匹配的准备结果失效。旧响应不能覆盖新步骤。
5. setter / action 引用稳定；读取和写入共享状态的 effect 依赖使用具体 session/step，不依赖整个 context 对象，防止重现反复获取的循环。

### 6.3 两个推进方向

**Quiz → Transition：**

1. 当前选项持续显示；等待 answer 成功。
2. 取得真实 `next_step` 后，如目标需要 metadata，调用一次 `getFlowState` 准备目标数据；与既有成功后 150ms 反馈并行进行。
3. 验证响应会话和步骤仍匹配。数据齐备后跳转，目标页直接消费已准备结果。
4. 必要数据获取失败时，保留当前内容并提供“继续加载”入口；后端可能已推进，此时重试准备/恢复，不盲目重新提交答案。

**Transition → Quiz：**

1. 请求期间保留过渡页正文和按钮位置。
2. Continue 成功后更新已确认步骤，使用当前会话配置和答案快照准备目标题目，再跳转。
3. 暖进入的目标题不再跑完整 session/config bootstrap。
4. Transition-5 的弹窗与 interstitial 顺序继续走已有流程，不因通用准备逻辑重复打开、重复提交或提前进入 email。

### 6.4 Continue 启用条件与冷进入

- 正常推进且有匹配的服务器确认依据、必要数据 ready：初次渲染即可操作，不重复等待相同的验证请求。
- 直接打开 URL、刷新、浏览器历史恢复、会话不匹配或冲突恢复：先走现有服务端恢复；不能用 URL 或旧快照直接开放 Continue。
- 409 时重新取得当前服务端步骤并定位；请求失败保留可恢复界面。
- 不承诺缓存能感知其他标签页的所有变更；即使暖路径可点击，最终推进接口仍必须检查当前步骤。

### 6.5 路由准备与效果边界

根据当前会话配置或服务端返回结果预取少量合理的目标路由，避免硬编码另一份步骤映射。带查询参数的预取是否有效，以生产构建下网络记录和录屏为准。

预取和数据缓存可以减少中间态，但不能保证不同路由之间完全不出现 fallback。不得仅凭“加了 prefetch”判定闪烁已经解决。

### 验收

- 已有 warm session/config 路径在 quiz↔transition 推进中不重复请求这两个 bootstrap API。
- 同一个目标步骤的数据准备不重复发起相同 flow-state 请求。
- 正常暖进入 Continue 无额外“先禁用后启用”阶段；冷进入仍有明确恢复过程。
- 确认结果只提交一次，旧响应、Back、刷新、409 和会话切换不造成错题或错误推进。
- 正常网络与注入 500ms 延迟下，录屏确认阶段切换没有“完整内容 → 全页 spinner/skeleton → 完整内容”的中间替换。

**最后一项是效果门槛：** 如果前面的优化仍无法满足，就不能把“spinner 换了颜色”当成完成，进入下述批次 3B。

## 7. 批次 3B：持续挂载的流程视图（条件执行）

**触发条件：** 批次 3 后，阶段切换仍出现用户可见的整块加载替换。  

1. 先写小范围 ADR，确认 quiz/loading 的 URL、刷新、浏览器历史和服务端恢复如何衔接；在本项目 Next 版本上做最小路由验证。
2. 抽出 `QuizView` 和 `TransitionView`。由两条路由共享的、持续挂载的 `QuizFlowHost` 持有当前视图和准备状态，复用批次 3 的数据控制逻辑。
3. 路由入口负责首次定位和恢复；流程内部在服务器确认、目标数据齐备后直接切换 host 的视图，不重复装载整个问卷。
4. URL 同步不能触发全量初始化；直接访问两个原 URL 均能正确启动。离开问卷范围仍走正常路由。
5. 不直接在现有两条路由各复制一套 host，也不只把跨路径 `router.push` 替换成 `history.replaceState` 就宣称完成。
6. 导航桥接必须验证 pathname/searchParams、返回/前进、刷新与路由树一致性。原有 q→q 历史策略保持；跨阶段历史条目的恢复由服务端判定，不增加新的业务 Back 语义。
7. 任意异步准备过程中保留当前完整视图；成功后一次切换。初次冷进入才显示全页初始化状态。

**验收：** 批次 3 的全部恢复和防重检查，以及 warm quiz↔transition 全程没有整块 fallback 替换；进入其他 soulmate 路由、再返回也无双重 host、重复埋点或状态泄漏。

这是架构调整，不能混进“改几个 CSS”的工作量。若触发，先登记任务与 ADR，再按该批次范围实施。

## 8. 批次 4：日期滚轮状态隔离

**优先级：中；可在批次 3 稳定后执行**

### 修改范围

`WheelDatePicker.tsx`、`quiz/page.tsx` 中日期提交的最小联动，以及对应交互验证。

### 具体实现

1. `WheelDatePicker` 内部维护完整日期 draft；每列滚动只更新局部索引，不逐行向 QuizPageContent 更新日期。
2. 滚动结算优先使用经目标浏览器验证的结束事件；不支持时采用约 100ms 无新滚动事件的定时回退。原分析的 80ms 仅作为调参参考。
3. RAF 只用于帧内合并视觉更新，不能用它表示吸附已完成。结算要检查最终位置，程序吸附完成前保持 moving 状态。
4. 首次挂载、答案恢复使用直接定位；用户点击远处行才平滑滚动。程序定位与用户手势分开标记，避免中途经过的行成为最终提交值。
5. 任一列 moving 时暂时禁用 Next；全部列稳定后一次提交完整日期 draft 给父级，再启用 Next。此方式优先于读取尚未结算的值。
6. 年/月改变时在组件内完成天数钳制，保证闰年、月末和多列操作后日期有效；外部恢复值必须能覆盖本地 draft。
7. 清理离页/禁用后的定时器、事件和过期回调，保证已恢复的新值不被旧结算覆盖。
8. 保留原生滚动和 scroll-snap；复用稳定的年份/月数组。仅在性能记录显示需要时再加 memo，不默认引入虚拟列表或 GPU 样式。
9. 首轮保留当前白色日期卡片的覆盖层。Mask 属于视觉选择，只有发现具体边缘缺陷才改。

### 验收

- 年/月/日连续快速操作、点远处行、惯性滚动后，显示值与实际提交值一致。
- 滚动中不能误提交旧日期；停止后 Next 正常恢复，无永久禁用。
- 2 月、闰年、30/31 天切换和 Back 恢复正确。
- 滚轮逐行变化不再触发整个 QuizPageContent 的逐行更新。
- 在真实 iOS/Android 记录手势和帧时间，与基线对比；不能用静态渲染测试宣称 60fps。

## 9. 验证、交付与执行顺序

### 验证矩阵

| 类别 | 必测内容 |
|---|---|
| 浏览器视口 | 320×667、375×667、390×844、430×932、768×1024、1440×900 |
| 真实移动设备 | iOS Safari / Android Chrome；地址栏、旋转、键盘、安全区、滚轮惯性 |
| 内容 | 单选、生日、多选长列表、各 Transition、Transition-5 弹窗、email 边界 |
| 网络 | 正常、注入 500ms 延迟、离线/失败、恢复与重试 |
| 步骤恢复 | 直接 URL、刷新、产品内 Back、浏览器历史、409/旧标签页、会话变化 |
| 生命周期 | 反复 quiz↔transition，无重复 bootstrap、循环 GET、重复埋点或残留计时器 |

当前 Vitest 为 node 环境，现有滚轮测试主要覆盖辅助逻辑/静态渲染。恢复、过期响应、防重和定时结算可加针对性自动测试；真实滚动/生命周期交互需浏览器验证，不能用现有静态测试替代。优先复用现有浏览器工具；若新增测试依赖，将其单独记录。

在 `frontend/` 执行并记录实际结果：

```sh
npm test -- tests/option-card.test.tsx tests/quiz-connect.test.tsx tests/transition.test.tsx tests/wheel-date-picker.test.tsx tests/quiz-shell.test.tsx
npm run typecheck
npm run lint
npm run build
```

新增的针对性测试同时加入窄范围命令。`build` 的 prebuild 会同步 canonical quiz JSON，执行后检查 diff，不把同步产生的无关变化混入 UI 修改。
